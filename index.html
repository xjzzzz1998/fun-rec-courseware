4. 整体架构：先建立一张地图

这不是一个“只训练模型”的项目，而是一条从离线资源到在线页面的完整链路。

用户 / 前端Vue 首页、登录、评分
FastAPI接收请求、补全特征
推荐流水线冷启动 → 召回 → 精排 → 重排

阅读提醒：README 描述了完整能力，但当前 RecallService 默认只启用了 UserPreferenceRecallStrategy；YoutubeDNN、Item-Item、热门召回在默认列表中是注释状态。先学会区分“实现了什么”和“默认打开了什么”。
离线时间线

在线时间线

反馈闭环

用户评分 → PostgreSQL、Redis、Elasticsearch、UCB 统计更新 → 影响下一次推荐。

9. 召回：先从很多电影中筛候选

召回追求“别漏掉可能喜欢的内容”，不是直接决定最终展示顺序。

RecallService 做了三件事

读取用户状态

从 Redis 读取 user:{id}:profile 和 user:{id}:history，补充请求中的用户特征。

并行调用策略

用 asyncio.gather() 同时执行多个召回通道，避免串行等待。

蛇形合并去重

轮询不同来源，交替取候选，并按 movie_id 去重。

几种召回策略

策略核心思路是否需要在线模型推理
偏好类型召回根据用户常见类型去 Elasticsearch 查询电影不需要，主要是检索
热门召回按评分数、平均分等条件查询热门电影不需要
Item-Item最近看过的电影向量，与物品向量做点积通常只需向量计算
YoutubeDNN用户行为 → 用户向量 → 与物品向量相似度 Top-K需要生成用户向量
点击查看 YoutubeDNN 在线路径
user_features
  → preprocess_user()
  → user_model.predict()
  → user_emb
  → np.dot(user_emb, item_embedding_matrix.T)
  → Top-K movie_id

物品向量通常由离线任务生成；用户向量可以在请求时根据最新行为生成。当前仓库默认没有启用该策略，需要在 online/recall/service.py 中打开它。

10. 精排：给候选打分

候选数量已经缩小后，才适合使用更复杂的排序模型。

DeepFM 的在线推理

候选电影 100 条
  → _prepare_batch_inputs()
  → 每条组成一个“用户-电影”样本
  → ranking_model.predict(...)
  → 按 CTR 预测分数降序排列
  → 取 top_k = 20

用户特征会复制到候选批次的每一行；电影 ID、类型、年份等物品特征随候选变化。模型的分数可以理解为“这个用户对这部电影的预测点击/喜欢程度”。

工程关键：RankingResourceManager 使用单例和懒加载，让模型常驻进程内存；如果 DeepFM 不可用，就回退到按召回分数排序。

推荐你重点读的文件

backend/online/ranking/service.py策略选择、top_k、模型重载、降级
backend/online/ranking/deepfm.py特征编码、批量输入、predict、按分数排序
backend/online/ranking/resource_manager.py加载 SavedModel、词表、模型配置

11. 重排与冷启动

模型排序之后，再用普通业务代码改善体验和覆盖边界情况。

重排：多样性打散

RerankingService 按链式顺序执行策略：

DeepFM 结果
  → GenreDispersionStrategy
  → DecadeDispersionStrategy
  → 最终列表

例如“最多连续两个相同类型”。违反约束的电影先放入 deferred，遇到合适位置再插入。这是可解释的贪心式策略，不必再训练一个神经网络。

冷启动：没有历史怎么办

默认历史交互少于 5 条，就走冷启动路径：

UCB 类型探索
  → 用户声明偏好
  → 热门电影回退

评分接口还会把新行为写回 PostgreSQL、Redis、Elasticsearch，并更新 UCB 类型统计，让下一次请求看到更近的用户状态。

12. 代码带着读：从请求走到结果

这一节不追求逐字背诵，而是每读一段代码，都明确“它拿到什么、改了什么、交给谁”。

12.1 推荐接口：它为什么只是一个“薄壳”

文件：`backend/app/api/v1/endpoints/recommendations.py` 查看原代码 ↗

@router.post("/recommend")
async def recommend(features: UserFeaturesRequest, db: Session = Depends(get_db)):
    pipeline = get_pipeline()

    user_features = await enrich_user_features(features, db)

    async def item_features_provider(movie_ids: List[int]) -> dict:
        return await get_item_features(movie_ids, db)

    result = await pipeline.recommend(
        user_features=user_features,
        item_features_provider=item_features_provider,
        config=PipelineConfig(recall_top_k=recall_k, ranking_top_k=top_k),
    )

    items = enrich_with_metadata(result, db)
    return RecommendationResponse(
        items=items,
        recall_count=result.recall_count,
        ranking_strategy=result.ranking_strategy,
    )

逐段解释

  1. `get_pipeline()` 返回推荐流水线单例，避免每次请求重复创建模型服务。
  2. `enrich_user_features()` 负责补齐用户历史和人口统计信息；API 层只负责数据准备。
  3. `item_features_provider` 是一个延迟查询函数，流水线需要候选电影特征时才调用它。
  4. `pipeline.recommend()` 才是真正的业务核心：冷启动、召回、精排和重排都在这里。
  5. `enrich_with_metadata()` 把电影 ID 变成前端需要的标题、类型和海报。

为什么这样分层

HTTP 层不应该塞满推荐规则。这样做以后，命令行测试、定时任务或其他接口也可以复用同一个 `RecommendationPipeline`。

阅读问题：如果把“召回 → 精排 → 重排”直接写在 API 函数里，会导致什么？提示：难测试、难复用、难替换模型。

12.2 总流水线：先判断冷启动，再走正常路径

文件：`backend/online/pipeline.py` 查看原代码 ↗

async def recommend(self, user_features, item_features_provider=None, config=None):
    config = config or PipelineConfig()

    if config.enable_cold_start and self._is_cold_start(user_features, config):
        return await self._cold_start_recommend(
            user_features, item_features_provider, config
        )

    candidates = await self._recall(user_features, config.recall_top_k)
    if not candidates:
        return RecommendationResult()

    ranked_items, ranking_strategy = await self._rank(
        user_features, candidates, item_features_provider,
        config.ranking_top_k, config.enable_ranking
    )

    reranked_items, reranking_strategies = await self._rerank(
        ranked_items, user_features, item_features_provider,
        config.enable_reranking
    )
代码它在做什么学习时要问什么
`config = config or ...`没有传配置时使用默认参数，例如召回 100 条、最终取 20 条。哪些参数会影响延迟和结果数量？
`_is_cold_start()`把新用户路由到另一条更适合少量数据的路径。为什么新用户不能直接使用完整模型？
`_recall()`先拿到一批候选，不直接返回最终列表。为什么不能对全部电影做精排？
`if not candidates`召回为空时安全返回空结果。实际生产中还能加什么兜底？热门榜、缓存？
`_rank()`调用 DeepFM 或 fallback，对候选评分。模型不可用时怎么保证服务继续？
`_rerank()`在模型排序之后执行多样性和业务策略。为什么把业务约束放在模型后面？

12.3 召回编排：并行执行，再轮询合并

文件：`backend/online/recall/service.py` 查看原代码 ↗

tasks = []
for strategy in self.strategies:
    tasks.append(strategy.recall(user_features, top_k))

results_list = await asyncio.gather(
    *tasks, return_exceptions=True
)

return self._merge_results_round_robin(results_list, top_k)

逐行读

  • 每个 `strategy` 都遵循同一个 `recall()` 接口，所以可以自由增删策略。
  • `tasks` 存的是异步任务；它们不需要串行等待。
  • `asyncio.gather()` 并发等待多个召回来源，降低总耗时。
  • `return_exceptions=True` 让一个策略失败时，其他策略仍可返回结果。
  • 最后交给轮询合并函数，负责多样性和去重。

轮询合并的直觉

偏好：A B C D
热门：E F G H
相似：I J K L

结果：A E I B F J ...

如果直接把三个列表首尾拼接，前面的召回源可能霸占所有位置；轮询合并让不同来源都有机会进入候选池。

12.4 DeepFM 精排：同一个用户，批量比较多部电影

文件：`backend/online/ranking/deepfm.py` 查看原代码 ↗

inputs = self._prepare_batch_inputs(user_features, candidates)

predictions = self.resource_manager.ranking_model.predict(
    inputs,
    verbose=0,
    batch_size=min(len(candidates), 256),
)

ranked_results = []
for i, candidate in enumerate(candidates):
    ranked_results.append({
        "movie_id": candidate["movie_id"],
        "score": float(predictions[i]),
        "recall_score": candidate.get("score", 0.0),
        "recall_type": candidate.get("recall_type", "unknown"),
    })

ranked_results.sort(key=lambda x: x["score"], reverse=True)

关键理解：这里不是给用户生成一个分数，而是给“用户 + 每一个候选电影”生成一行输入。用户特征在批次中重复，电影特征随候选改变，模型输出每部电影的预测分数。

两个分数不要混淆：`recall_score` 是召回阶段的分数；`score` 是 DeepFM 精排分数。最终排序主要使用后者，但保留前者便于调试和分析。
为什么要使用 batch_size？

候选可能有几十到几百条，一次批量预测比逐条调用模型更高效。代码把批大小限制在 256 以内，是一个简单的内存和吞吐折中。

12.5 重排：不改模型分数，只改变列表顺序

文件：`backend/online/reranking/dispersion.py` 查看原代码 ↗

for item in items:
    if self._can_add(item, result):
        result.append(item)
        self._try_insert_deferred(result, deferred)
    else:
        deferred.append(item)

result.extend(deferred)
  1. 按原本的高分顺序逐个读取电影。
  2. `_can_add()` 检查加入后是否会让同一类型连续超过阈值。
  3. 可以加入就放入结果；不可以就暂存到 `deferred`。
  4. 每加入一个新类型的电影，就尝试把暂存内容中现在合适的电影插进来。
  5. 最后仍无法插入的内容追加到末尾，保证不会丢内容。
工程启发：排序模型解决“用户可能喜欢什么”，重排策略解决“最终列表是否好看、是否重复、是否满足业务约束”。两者职责不同。

3.1 后端入口：FastAPI 如何启动

文件：`backend/app/main.py`

app = FastAPI(

3.2 前端 API 层：axios 如何封装后端请求

文件：`frontend/src/services/api.js`

const API_BASE_URL =
  import.meta.env.VITE_API_URL || 'http://localhost:8000'

const api = axios.create({
  baseURL: ${API_BASE_URL}/api,
  timeout: 10000,
})

getRecommendations(userId, topK = 20) {
  const token = localStorage.getItem('token')
  return api.post(
    '/recommendations/recommend',
    { user_id: userId },
    {
      headers: { 'Authorization': 'Bearer ' + token },
      params: { top_k: topK }
    }
  ).then(response => {
    return { ...response, data: response.data.items }
  })
}
代码作用
axios.create()统一设置后端地址、API 前缀和请求超时。
localStorage.getItem('token')取登录后保存的 JWT，放进 Authorization 请求头。
api.post(...)发送用户 ID 和 top_k，调用后端推荐接口。
response.data.items后端返回的是包含元数据的对象，前端这里提取电影数组以兼容原有组件。

前端组件不应该自己拼接 URL、处理 token 和解析接口结构，这些事情集中放在 services/api.js 更容易维护。

3.3 Home.vue：页面什么时候发起推荐请求

文件：`frontend/src/views/Home.vue`

const forYouMovies = ref([])
const loadingForYou = ref(false)

const fetchRecommendations = async () => {
  if (!authStore.isAuthenticated || !authStore.user) {
    forYouMovies.value = []
    return
  }

  loadingForYou.value = true
  try {
    const response = await movieApi.getRecommendations(
      authStore.user.user_id
    )
    forYouMovies.value = response.data
  } catch (error) {
    console.error('Failed to fetch recommendations:', error)
  } finally {
    loadingForYou.value = false
  }
}

onMounted(() => {
  if (authStore.isAuthenticated) {
    fetchRecommendations()
  }
})
  1. ref([]) 创建响应式数组；请求完成后，模板会自动刷新。
  2. 未登录用户不请求个性化推荐，forYouMovies 置为空。
  3. 请求开始时设置 loading，失败时记录错误，最后无论成功失败都关闭 loading。
  4. onMounted() 表示页面首次挂载后发请求；文件中还用 watch() 在登录状态变化时重新触发。
前后端连线：这里的 movieApi.getRecommendations() 对应后端的 POST /api/v1/recommendations/recommend，返回的 items 最终写进 forYouMovies。

1. 小白语法补给：先把代码读懂

这些不是推荐算法，但它们会反复出现在项目源码里。先掌握它们，后面的业务代码会轻松很多。

1.1 函数、参数和返回值

def add(a: int, b: int = 0) -> int:
    return a + b

result = add(3, 4)
  • def 定义函数，a 和 b 是参数。
  • : int 是类型提示，告诉读代码的人“这里期望整数”；Python 不会仅因为提示自动强制转换。
  • b: int = 0 表示 b 有默认值，调用 add(3) 也可以。
  • -> int 表示预期返回整数。
  • return 把结果交给调用者。

1.2 字典、列表和列表推导式

user = {
    "user_id": 1,
    "hist_movie_ids": [1193, 661, 914],
}

movie_ids = user["hist_movie_ids"]
new_ids = [movie_id for movie_id in movie_ids if movie_id != 661]
  • 字典用键访问值：user["user_id"]。
  • 列表保存有顺序的一组数据，推荐系统中经常保存行为序列。
  • 列表推导式等价于“循环 + 条件 + append”，只是更紧凑。
  • 项目里的 user_features、候选电影和模型输入，很多都是字典套列表。

1.3 async / await：为什么接口函数前面有 async

async def recommend():
    user = await load_user()
    items = await recall(user)
    return items

async def 定义异步函数；await 表示“等待这个异步任务完成，但在等待网络/数据库时可以让出执行权”。

在本项目里，读取数据库、调用 Elasticsearch、并行召回都可能是等待型工作。异步不等于模型自动变快，它主要帮助服务同时处理更多请求。

tasks = [
    strategy.recall(user_features, top_k)
    for strategy in strategies
]
results = await asyncio.gather(
    *tasks,
    return_exceptions=True,
)

这里先准备多个协程，再用 gather 一起等待，避免召回策略一个接一个串行执行。

1.4 装饰器：@router.post 到底是什么

@router.post("/recommend")
async def recommend(features):
    return {"items": []}

可以把装饰器理解成“给函数登记用途”。FastAPI 看到 @router.post("/recommend") 后，就知道：收到 POST /recommend 请求时，调用下面这个函数。

它大致相当于先定义函数，再把函数交给一个注册器：

async def recommend(features):
    return {"items": []}

router.post("/recommend")(recommend)

1.5 yield：数据库为什么不是 return db

def get_db():
    db = SessionLocal()
    try:
        yield db          # 暂时把 db 交给路由
    finally:
        db.close()        # 路由结束后清理

yield 会暂停函数，把一个值临时交出去；当外层使用结束后，函数从暂停位置继续执行。因此这里很适合表达“借你一个数据库会话，用完一定关闭”。

1.6 Depends：FastAPI 的依赖注入

@router.get("/movies")
async def get_movies(db: Session = Depends(get_db)):
    return db.query(Movie).limit(20).all()

你没有手动调用 get_db()，FastAPI 会看到 Depends(get_db)，自动执行它，把返回的数据库会话放入参数 db。这叫依赖注入。

认证代码也是同一机制：Depends(get_current_active_user) 会先完成 token 验证，再把当前用户传给接口。

1.7 Vue 的 ref、computed、watch、onMounted

const movies = ref([])
const count = computed(() => movies.value.length)

onMounted(() => {
    loadMovies()
})

watch(
    () => authStore.isAuthenticated,
    (loggedIn) => {
        if (loggedIn) loadMovies()
    }
)
  • ref([]) 创建响应式变量；在 JavaScript 中读取值要写 movies.value。
  • computed 根据其他状态自动计算；电影数组变化时 count 会更新。
  • onMounted 在组件第一次出现在页面后执行，适合发起初始请求。
  • watch 监听一个值的变化，例如用户从未登录变成已登录。

1.8 Vue 模板的 v-if、v-for、props

  • v-if 根据条件决定是否渲染。
  • v-for 把数组中的每个电影变成一个组件。
  • :key 帮 Vue 识别列表中的稳定身份。
  • :movie="movie" 把父组件变量传给子组件的 prop。

1.9 读错误处理：try / except / finally

try:
    result = await call_service()
except Exception as error:
    logger.error("推荐失败: %s", error)
    result = fallback_result()
finally:
    release_resource()

try 放可能失败的代码，except 处理异常，finally 无论成功失败都执行。推荐服务里经常需要降级，而不是让一次模型或搜索失败导致整个首页报错。

def get_password_hash(password: str) -> str:
    salt = bcrypt.gensalt()                     # 每次密码使用随机盐
    hashed = bcrypt.hashpw(password.encode("utf-8"), salt)
    return hashed.decode("utf-8")

def verify_password(plain_password, hashed_password):
    return bcrypt.checkpw(
        plain_password.encode("utf-8"),
        hashed_password.encode("utf-8"),
    )

def create_access_token(data: dict, expires_delta=None):
    to_encode = data.copy()
    expire = datetime.now(timezone.utc) + (
        expires_delta or timedelta(
            minutes=settings.access_token_expire_minutes
        )
    )
    to_encode.update({"exp": expire})
    return jwt.encode(
        to_encode, settings.secret_key,
        algorithm=settings.algorithm,
    )

def decode_access_token(token: str):
    try:
        return jwt.decode(
            token, settings.secret_key,
            algorithms=[settings.algorithm],
        )
    except jwt.JWTError:
        return None

async def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security),
    db: Session = Depends(get_db),
):
    token = credentials.credentials               # Bearer 后面的字符串
    payload = decode_access_token(token)
    if payload is None:
        raise HTTPException(status_code=401, detail="无法验证凭证")

    user_id = int(payload.get("sub"))             # sub 保存用户 ID
    user = db.query(User).filter(
        User.user_id == user_id
    ).first()
    if user is None:
        raise HTTPException(status_code=401, detail="用户不存在")
    if not user.is_active:
        raise HTTPException(status_code=403, detail="用户未激活")
    return user

async def get_current_admin_user(
    current_user: User = Depends(get_current_user),
):
    if not current_user.is_superuser:
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return current_user

  if (!token.value) return
  const response = await axios.get(
    API_BASE_URL + "/api/users/me",
    { headers: { Authorization: "Bearer " + token.value } },
  )
  user.value = response.data
  localStorage.setItem("user", JSON.stringify(user.value))
}

function logout() {
  user.value = null
  token.value = null
  localStorage.removeItem("token")
  localStorage.removeItem("user")
}

8. 算法结构详解：代码背后的数学和数据流

这一节回答“模型为什么这样组织”，并把训练阶段和在线阶段接起来。

8.1 总体结构：两阶段推荐

用户行为评分、历史电影
召回100 条左右
粗候选多源合并去重
精排DeepFM 分数
重排多样性和业务规则
最终列表返回前端

为什么要分两阶段？全站可能有数千甚至数百万个物品。先用快速方法找出几百个候选，再对候选使用较重的排序模型，可以在效果和延迟之间取得平衡。

召回的目标：高覆盖率，尽量不漏掉用户可能喜欢的电影。
精排的目标：高准确率，把最可能点击/喜欢的候选排到前面。

8.2 特征编码：为什么代码里总是出现整数 ID

原始数据中的 gender、genres、movie_id 是字符串或业务值，Embedding 层通常需要整数索引。因此离线预处理会建立词表：

LabelEncoder.fit_transform(raw_values)
    → 0, 1, 2, 3, ...

1
    → 1, 2, 3, 4, ...
    → 0 专门保留给 padding / unknown

在线推理时，ResourceManager.encode_feature() 使用同一份词表把原始值转成整数。训练和推理必须使用同一份编码规则，否则模型看到的 ID 含义会错位。

用户特征

user_id、gender、age、occupation、zip_code

电影特征

movie_id、genres、isAdult、startYear

8.3 YoutubeDNN：双塔召回算法

文件：`src/funrec/models/youtubednn.py`、`backend/offline/training/train_retrieval.py` 打开模型源码 ↗ 打开训练源码 ↗

用户塔
用户 ID + 人口统计 + 历史电影/类型
→ Embedding 聚合
→ DNN
→ 用户向量 u
相似度
物品塔
电影 ID
→ Embedding
→ 物品向量 v

在线召回时计算：

score(user, movie) = cosine(u, v)
                    ≈ dot(normalize(u), normalize(v))

取 score 最高的 Top-K 电影

模型构建代码如何读

user_dnn_inputs = concat(
    user_feature_embedding,
    hist_seq_embedding,
)

user_dnn_output = DNNs(
    units=dnn_units + [emb_dim],
    activation="relu",
)(user_dnn_inputs)

user_dnn_output = L2NormalizeLayer(axis=-1)(user_dnn_output)
  1. 不同离散特征先查 Embedding 表，得到多个向量。
  2. 历史电影和历史类型经过聚合，形成用户近期兴趣表示。
  3. 把用户画像向量和历史兴趣向量拼接后输入 DNN。
  4. 最后输出固定维度的用户向量，并做 L2 归一化，方便用点积表示余弦相似度。

训练目标：采样 Softmax

训练时不可能让每条用户行为都和全部电影比较，因此对一个正电影采样若干负电影，让模型提高正样本相似度、降低负样本相似度。

正样本：用户实际评分过的电影
负样本：随机采样的其他电影

loss = sampled_softmax(
    user_vector,
    positive_movie_id,
    sampled_negative_movie_ids
)
在线对应关系：物品向量矩阵由离线训练后保存；在线只需要根据最新用户行为生成用户向量，再做矩阵点积。

8.4 召回训练样本：滑动窗口如何制造“历史 → 下一部电影”

文件：`backend/offline/feature/preprocess_retrieval.py`

用户行为序列：A → B → C → D

训练样本：
历史 [A]       目标 B
历史 [A, B]    目标 C
历史 [A, B, C] 目标 D

测试样本：
历史 [A, B, C] 目标 D

代码先按时间排序，再对每个用户生成滑动窗口。这样模型学习的是“根据已经发生的行为，预测下一部可能发生的电影”，比随机打乱更接近线上推荐。

8.5 DeepFM：线性项 + FM 二阶交叉 + DNN 高阶交叉

文件：`src/funrec/models/deepfm.py`、`backend/offline/training/train_ranking.py` 打开模型源码 ↗ 打开训练源码 ↗

稀疏特征
用户、电影、类型、年份
Embedding
三条支路
Linear
FM
DNN
相加
Sigmoid
CTR 分数

模型结构

linear_logit = 一阶特征贡献

fm_logit = Σ<i,j> <v_i, v_j> x_i x_j
           # 捕捉两两特征交互

dnn_logit = MLP(flatten(embeddings))
            # 学习更高阶的组合

deepfm_logit = linear_logit + fm_logit + dnn_logit
prediction = sigmoid(deepfm_logit)

直觉例子：user_id 单独有一个偏好，genres 单独有一个偏好；FM 可以学习“某类用户 × 某类型电影”的二阶交互，DNN 可以继续学习更复杂的组合。

代码中的三条支路

fm_out = FM()(concat_feature)

dnn_out = DNNs(
    units=[128, 64, 32, 1],
    dropout_rate=0.1,
)(Flatten()(concat_feature))

linear_logit = get_linear_logits(...)
deepfm_logits = add(fm_logit, dnn_logit)
output = Dense(1, activation="sigmoid")(deepfm_logits)

在线阶段，ranking_model.predict() 只执行前向计算；训练阶段才会通过二元交叉熵更新参数。

8.6 DeepFM 的训练样本：正样本、困难负样本、随机负样本

文件：`backend/offline/feature/preprocess_ranking.py`

样本类型来源为什么有用
正样本用户评分达到个人平均分附近的电影代表较强的正向兴趣
困难负样本用户曝光过但没有点击/正向互动的电影最接近真实竞争场景，区分度高
随机负样本用户从未交互过的电影扩大负样本覆盖，帮助模型建立边界
positive_samples = df[df["is_click"] == 1]
hard negatives = exposed but is_click == 0
random negatives = movies user never interacted with

训练标签：
is_click = 1  # 正样本
is_click = 0  # 负样本

这里的 is_click 是基于 MovieLens 评分构造的教学标签，不是线上真实埋点中的点击事件。读项目时要注意“演示数据如何模拟真实业务信号”。

8.7 UCB 冷启动：探索与利用

文件：`backend/online/cold_start/ucb_genre.py`。当用户行为很少时，系统不能只推荐当前看起来最好的类型，否则可能永远发现不了新偏好。

UCB(genre) = average_reward(genre)
              + c * sqrt(ln(total_trials) / genre_trials)

第一项：利用，偏好过的类型
第二项：探索，尝试样本少的类型

在这个项目里，评分行为会更新 Redis 中的类型统计；冷启动服务根据 UCB、用户声明偏好和热门电影分配推荐数量。

UCB 不是神经网络，但它解决了推荐系统很重要的问题：在不了解用户时，既要利用已有信号，也要主动探索。

8.8 多样性重排：一个可解释的贪心算法

重排的约束可以写成：

若 recent_genres[-2:] 都等于 item.genre：
    暂不加入，放入 deferred
否则：
    加入结果列表

它不改变每部电影的模型分数，只改变最终排列。优点是简单、低延迟、可解释；缺点是它不是全局最优，可能为了多样性牺牲一些高分内容。
